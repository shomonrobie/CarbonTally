CarbonTally RC1 — Independent Database Audit
Auditor: Independent Principal Database Architect (not the migration author)
Scope: database/rc1 at github.com/shomonrobie/CarbonTally @main — 001_rc1_schema.sql … 007_rc1_verification.sql
Method: full static review of all seven files against the 100-table baseline schema dump; PostgreSQL 16 grammar parse of every file (pglast — all seven parse cleanly); programmatic cross-checks of every referenced table/column against the baseline; penetration-style review of every RLS policy, function and trigger. No files were modified. No replacement SQL is provided.
Executive Summary
The migration is well-documented, disciplined in intent (verify-first, idempotent guards, NOT VALID + VALIDATE, honest caveats), and its structural core — renames, the 36-table tenant array, the constraint arithmetic — is largely correct and was verified programmatically. It is nonetheless not production-ready: it contains a one-line defect that aborts the migration on its first run, and three independent critical security holes, any one of which would fail a UK launch gate. The defects are concentrated and fixable; the architecture underneath is sound.

Critical Issues (Must Fix)
C1 — Migration aborts on first run: unconditional COMMENT on a column that does not exist
Problem. 001_rc1_schema.sql:259 executes COMMENT ON COLUMN public.emission_factors.region_deprecated unconditionally. The baseline dump's factor table has no region column; the C4 guard block (001:220–242) correctly detects this, takes its ELSE branch, and never creates region_deprecated. The COMMENT then raises error 42703 and aborts file 001's transaction mid-file.
Evidence. 001:259 (COMMENT, unconditional) vs 001:236 (rename to region_deprecated exists only inside the IF branch); the author's own ELSE-branch comment proves the absence was known.
Risk. Because 002 (K1, F1), 003, 004 and 006 all reference emission_factors or renamed columns, the entire chain 001→007 fails when executed from an empty database built from the actual baseline — the exact scenario Area 1 of this audit was asked to prove.
Impact. Total migration failure on run 1; rollback/forward-fix cycle required before any other finding matters.
Severity. Critical.
Recommendation. Move the COMMENT inside the existence-guarded branch (or guard it on column existence). One-line fix; no design change.
C2 — 51 tables left with no RLS at all, including credential-bearing and PII tables
Problem. 004_rc1_rls.sql:133–171 enables RLS on exactly the 36 organization_id-bearing tables (verified: 36/36 exact match to the dump), plus organizations/users/notifications and 10 reference tables. Everything else in the 100-table schema receives no RLS whatsoever. Verified unprotected and sensitive: password_reset_tokens (live cleartext tokens, dump line 735), system_settings, consultant_profiles (PII, plaintext api_key, bank details), consultant_billing, consultant_firm_members, consultant_tasks, staff_profiles and the staff/QC/approval families, login_history (IP/UA PII), beta_users, waitlist, the audit/log families, conversation_participants, typing_status, user_presence, notification_delivery(_log), and — most damaging — child tables of protected parents: manual_extraction_items (extracted payloads, calculated emissions, file URLs) and report_versions (full report content), report_comments.
Risk. On Supabase, default privileges grant table access to anon/authenticated; a table with no RLS is fully readable/writable via PostgREST. Anonymous reading of password_reset_tokens is an account-takeover primitive. The file's own verification queries (004:340–356) and 007 §6 audit only org-id tables and the enabled-but-no-policy state — both are blind to this exact hole, so the RLS gate passes green while tokens leak.
Impact. Cross-tenant and unauthenticated exposure of credentials, staff and consultant PII, extraction payloads and report content at UK launch; GDPR breach on day one.
Severity. Critical.
Recommendation. Enable RLS (deny-by-default, with explicit service-role or parent-key-join policies) on every remaining public table; extend the verification script to list public tables with RLS disabled.
C3 — anonymise_user trusts a caller-supplied actor: any user can mass-erase any account
Problem. 005_rc1_functions.sql:114 computes the effective actor as coalesce(p_actor_id, auth.uid()), and EXECUTE is granted to authenticated (005:186). Any logged-in user can call the function with p_actor_id set to any known active staff user's UUID — and staff_profiles is one of the RLS-less tables in C2, so staff UUIDs are enumerable. Guard 1 passes; the victim is irreversibly anonymised.
Risk. The GDPR erasure artefact becomes a mass-erasure weapon: unauthenticated-equivalent, permanent destruction of identity data across tenants. By design there is no undo (005:86–88), and no audit row is written (H9), so abuse is also undetectable after the fact.
Impact. Catastrophic, irreversible data destruction; regulatory breach created by the compliance feature itself.
Severity. Critical.
Recommendation. Derive the actor exclusively from auth.uid() whenever it is present; honour p_actor_id only in the service context (auth.uid() IS NULL). One-guard fix.
C4 — Any organisation member can promote themselves to admin
Problem. The tenant-policy loop (004:209–214) is applied to organization_members (004:158) with membership-only predicates — no role check. Any member, at the lowest role, can UPDATE any membership row in their org (including setting their own role='admin') and INSERT new members.
Risk. organization_members.role is the column every API-layer authorisation decision keys on; the database itself lets any invited member rewrite it.
Impact. Full tenant takeover by any member; no DB-layer mitigation exists.
Severity. Critical.
Recommendation. Add role-based predicates (admin/owner) to the organization_members insert/update/delete policies.
C5 — Users can self-promote via the unrestricted self-update policy
Problem. users_self_update (004:274–278) is USING (id = auth.uid()) WITH CHECK (id = auth.uid()) with no column restriction. users carries user_type, is_active, email_verified and password_hash (dump line 1397).
Risk. Any user can self-promote user_type, self-verify their email, or reactivate a deactivated account — escalating into whatever staff/admin flows the API gates on user_type.
Impact. Role escalation from any authenticated session.
Severity. Critical.
Recommendation. Restrict the self-update column set (column privileges or a trigger); role/status columns must be service-role writes only.
C6 — Consultant cross-tenant model is broken in both directions
Problem. (a) The consultant tables (consultant_profiles, consultant_firm_members, consultant_tasks, consultant_billing) have no organization_id and received no RLS (see C2) — consultant PII, api_key, Stripe IDs and the client_access authorisation arrays are exposed. (b) Legitimate consultant access to client orgs flows through consultant_clients/client_access, not organization_members — so is_org_member() returns false and consultants are locked out of every client-org table: the workflow is dead at launch. (c) consultant_clients itself received the tenant policy (004:140), so a consultant cannot even read their own linkage rows. The I4 GIN index (003:95–96) is justified as serving "consultant RLS predicates" that were never created, and the release notes' consultant smoke test cannot pass as written.
Risk. Whichever way operations patches this creates either an outage or over-broad access: locking consultants out, or adding them as org members — which bypasses client_access scoping entirely and grants full read/write of every client org.
Impact. Launch-blocker for the consultant channel; potential cross-client exposure if patched via membership.
Severity. Critical.
Recommendation. Design and ship a dedicated consultant policy path (firm → client_access → org resolution) before sign-off; do not patch via membership grants.

Positive Findings

Zero phantom references: every table and column cited in 001–007 exists in the 100-table baseline dump (verified programmatically), including the subtle ones (users.email_verified, staff_profiles.is_active, units.code with its UNIQUE for the FK target).

The RLS helpers are genuinely recursion-free as shipped, with pinned search_path, no dynamic SQL (no injection surface), and EXECUTE revoked from PUBLIC.
No anonymous grants anywhere in 004; reference tables are SELECT-only for authenticated with no write path.
Tenant INSERT policies correctly carry WITH CHECK (membership + active-org), so cross-tenant insertion by setting organization_id fails.
Suspended orgs keep read access — SELECT policies deliberately omit the active check, so there is no data-hostage problem; only writes/delete freeze. Matches design intent.
NOT VALID + VALIDATE is correctly implemented throughout 002 (except where H2/H3 note): existing rows are never scanned under a write-blocking lock.
K6's defensive drop of the password_reset_tokens.user_id UNIQUE handles constraint-backed vs standalone indexes by definition, not name — genuinely robust; token UNIQUE untouched.

The queue-claim partial indexes will actually be used: predicates are verified subsets of the K4 status vocabularies for both processing queues; messages_conversation_created_idx supports keyset pagination and covers the one properly index-supported FK.
The constraint arithmetic is internally consistent: 53 CHECKs, 7 UNIQUEs, 11 FKs, 13 NOT NULLs, 18 indexes, ≤76 triggers and the ~160-policy upper bound all recount correctly against 007/008, and 007 is genuinely read-only.
Ireland structural enablers are coherent: the eircode column + presence CHECK + 'IE'/'EUR' IN-lists admit a complete Irish onboarding path (service-role org insert, eircode-only facility), and the Phase-B IE factor rows are legal under K1 (modulo H3's key).

Security Review
Score 36/100. The security architecture's intent is right — RLS-first isolation, helper-mediated policies, verify-first posture, an irreversible-by-design erasure procedure, secrets out of reach of PUBLIC — but three independent critical defects sit on the launch path. C2 is the most dangerous: on a stock Supabase project the 51 unprotected tables are world-readable via PostgREST, and the set includes the single worst table to leave open (password_reset_tokens) plus the content children of protected parents, which defeats the point of protecting the parents. The verification suite's blindness to this gap (it audits only org-id tables) converts a scoping error into a silent one. C3 turns the compliance crown-jewel into an attack primitive — the actor guard consults a caller-controlled parameter before the authenticated identity, and the irreversibility that makes the function GDPR-sound makes the exploit unrecoverable. C4/C5 are the same class of defect in two places: policies that check identity but never authority, on exactly the two tables whose columns downstream authorisation trusts (membership role, user type). The consultant model (C6) is broken symmetrically — its tables leak while its workflow is locked out — which guarantees a launch-day patch, and the obvious patch (membership grants) is itself a cross-client leak. Beyond the criticals: erasure never reaches auth.users (H5), so "erased" users retain working logins; org billing columns are member-writable (H6); storage objects sit outside every policy (M16); and deletes are hard deletes for any member (L14). The positives are real — recursion-free helpers, no anonymous grants, correct WITH CHECK discipline on the covered set — but they cover barely half the schema.
Performance Review
Score 64/100. At launch volumes (tens of customers, seed-scale tables) everything in this package performs fine: the queue-claim partial indexes are predicate-aligned with the K4 vocabularies and will be used; the messages composite supports keyset pagination; VALIDATE scans and the one table rewrite are trivial at these row counts. The problems are coverage and scale. Three of the busiest tables — both processing queues and the report queue — have no organization_id index at all (M7), so every RLS-checked tenant read seq-scans them; the audit/log families, flagged in the client's own scalability review as the fastest-growing tables, have no tenant/time composites (M7/M21). The RLS helpers are STABLE SECURITY DEFINER and therefore not inlined: every row on every policy-checked scan pays a function call and a membership probe (M21) — acceptable at 100 customers, a linear multiplier on report-size scans at 10,000. The trigram GINs are tenant-unscoped (M22), so autocomplete candidate sets grow with the whole platform's suppliers rather than the tenant's. Two indexes ship with rationales that are false as delivered: the client_access GIN serves policies that were never created (C6), and the report-queue claim partial is anchored to an unconstrained status vocabulary (M11); the VAT trigram is near-dead weight (L8). The lock profile is honestly labelled for a pre-launch window but never enforced — re-run at scale and the unique builds, rewrites and VALIDATEs become outages (M2, L16). Net: a sound core that will carry the first few hundred customers, with specific, nameable gaps before the 1,000-customer tier.
RLS Review
Score: fails the penetration gate. The covered core is genuinely good: the 36-table tenant set exactly matches the schema's org-bearing tables; every verb is covered per table; INSERT carries WITH CHECK; suspended tenants keep reads; helpers are injection-free, recursion-free and correctly permissioned; nothing is granted to anon; and no existing policy is weakened (there is no DROP/ALTER POLICY anywhere). The failure is everything outside that core. Fifty-one tables — credentials, staff and consultant PII, ops internals, messaging presence, and the content children of protected parents — have no policies and no RLS at all (C2), and the file's own verification queries cannot see the omission. Within the covered set, policy quality has a systemic weakness: predicates check membership, never authority — any member can rewrite roles (C4), any user can rewrite their own type (C5), any member can rewrite org billing and lifecycle columns (H6), messages are org-wide readable despite direct-message semantics (M14), and rows can be laundered between an attacker's own orgs (M15). The consultant channel — a first-class launch feature — has no valid access path at all (C6): its own tables are exposed while its legitimate workflow is locked out. The verify-first guards match policies by name, so a pre-existing weaker or permissive policy silently wins or unions (M17). Storage objects, the actual bytes behind every document row, are outside every policy in the package (M16). Verdict: the design is right and the implementation is half-finished; extend coverage to the full public schema, add authority predicates to the membership/user/org policies, and build the consultant path deliberately rather than by membership workaround.
Migration Safety Review
Score 34/100. The direct question — can these files execute successfully from an empty database built only from the baseline dump? — has a one-word answer as shipped: no. C1 aborts file 001 at line 259 on a COMMENT for a column the file itself knows does not exist; every subsequent file depends on 001's renames, so the whole chain fails on run 1. Past C1, the run faces three further abort hazards: H2's units FK, which validates against values the migration itself backfilled from a free-text column and can block forever; H3's unguarded unique build over a too-narrow natural key, which can hard-fail on legitimate factor duplicates; and M3's VALIDATE blast radius, where a single unmapped 'Éire' or '€' row rolls back the entire constraints file (fail-safe in direction, all-or-nothing in scope, with the leftover-violation report living in a script that runs only afterwards). Idempotency is real but name-based (M1): re-runs of these exact files are safe, but a target database carrying pre-existing objects under different names will collect duplicate FKs and CHECKs. The transaction strategy is otherwise sound — 001/002/004/005/006 are single clean transactions, 003 is correctly non-transactional for CONCURRENTLY with per-statement idempotency, though nothing enforces that execution mode on the Supabase CLI path (M5). Rollback guidance exists per file for every destructive operation, and the destructive set is genuinely small and non-destructive where it matters (region retired by rename, tokens' UNIQUE dropped after definition-based lookup). Data preservation is handled with the right patterns — backfill-then-constrain, fail-safe NULL guards, NOT VALID + VALIDATE — undermined in specific spots (K8's irreversible defaults without a snapshot, L1's dead backfill). The fix list for a passing safety score is short: the C1 one-liner, the H2/H3 constraint decisions, the M3 mapping hardening, and definition-based guards.
Final Recommendation
Would I approve this migration for production? NO.
Not because the design is wrong — the architecture, the constraint philosophy, the verify-first posture and the documentation discipline are the work of a competent team, and seventeen specific positive findings were verified under adversarial review. The refusal is because the package, as committed, fails the two tests a migration may never fail: it does not run (C1 aborts it on line 259 of the first file), and it does not protect the data (C2 leaves credentials and PII world-readable, C3 lets any user destroy any account, C4/C5 let any member seize the tenant). Add the consultant channel being simultaneously exposed and unusable (C6), an erasure procedure that fails at runtime (H1) and never touches the real credential store (H5), and a constraints file that can deadlock on its own backfill (H2), and no responsible sign-off is possible.
The encouraging part is the shape of the fix: one line for C1, one guard for C3, authority predicates for C4–C6, a coverage sweep for C2, and a small set of constraint corrections for H2–H4. None of it is redesign. Approve after: C1–C6 and H1–H5 are fixed; the verification script is extended to see the gaps it is currently blind to (non-org tables without RLS; trigger-coverage mismatches; leftover constraint violations before VALIDATE); the Gate 4 penetration matrix is re-run against actual policy expressions rather than names; and a staging data audit settles M3, H2 and H3 against real seed data. At that point this package becomes what it was clearly intended to be — a disciplined, launch-grade hardening migration.
Audit scope note: analysis was static against the repository files and the baseline schema dump; no live database was available. Findings dependent on actual row data (M3 mappings, H2/H3 duplicates, K4 vocabulary completeness) are risk-flagged rather than proven failures, and the files' own failure mode in those paths is loud-and-safe rather than corrupting.
